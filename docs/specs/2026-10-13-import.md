# Spec: the import

Slice 3 of the build order in [architecture.md](../architecture.md). Written 2026-10-13. Once the slice has shipped this file is history and is not kept up to date.

## Goal

Merge a file exported by hand from a bank's website into the archive, so that history the API cannot reach, and accounts it never reaches, are archived under the same rules as everything else.

After this slice the command `import <format> <file> [--write]` exists and is tested end to end against a temporary directory. Nothing in this slice runs in production: the first real import is the user's.

[sync.md](../sync.md) and [archive-format.md](../archive-format.md) are the design this spec builds. Where it differs from them, or settles what they left open, the point is listed under "Departures and additions" and is written into the document that owns it before the slice is done.

## What is already there

The archive-format slice built the parts of the import that are about the archive, so this slice does not:

- the import format's type and its validation, in `shared/src/config/config.ts`;
- the normalised view of an import record, in `shared/src/archive/normalise.ts`;
- `merge` for an `import` target, and the store's `import/` source.

What is missing is everything between a file on disk and a batch for `merge`.

## What the real files showed

The format schema was designed from documentation. Before this spec was written, the owner ran a profiler over two real export files, outside this repository's history. It printed their structure with every letter, digit and non-ASCII character masked, and no file name. Nothing else about them is recorded here, and no header name or value reached this repository.

- **Both fit the schema as it is.** A header on the first line, one delimiter, one signed amount column, an identifier column the owner confirms is unique and stable, and date notations the code already reads. No lines surround the table.
- **One file quotes every cell, and some cells hold the delimiter.** The reader must handle quoting properly.
- **One file has cells that hold a single space.** The view needs a rule for a blank cell.
- **One file wraps a text cell in single quotes**, which is not quoting in the sense of the format. If such a cell ever holds the delimiter, its row has too many cells and the file is rejected. That is left as a loud rejection; see "Not in this slice".

## What gets built

### Modules

All in the `sync` workspace. The reader is pure: bytes in, a result or a rejection out.

| Module                            | Does                                                                          | Pure |
| --------------------------------- | ----------------------------------------------------------------------------- | ---- |
| `src/import/decode.ts`            | Bytes to text, by the declared encoding, with the checks below.               | yes  |
| `src/import/delimited.ts`         | Text to a header and rows of cells.                                           | yes  |
| `src/import/rows.ts`              | A header and rows, a format and the accounts, to one batch per account.       | yes  |
| `src/import/characters.ts`        | The distinct non-ASCII characters of a text, each with a count.               | yes  |
| `src/commands/import.ts`          | Reads the file, runs the reader, merges, prints the summary, writes if asked. | no   |
| `src/main.ts`                     | Learns the command and its arguments.                                         | no   |
| `shared/src/config/config.ts`     | Rejects unknown keys, and an `id` column that another field also names.       | yes  |
| `shared/src/archive/normalise.ts` | Trims text cells of an import record, and treats a blank one as absent.       | yes  |

The reader lives in `sync` and not in `shared`, because only the command line ever reads an export file, and `shared`'s main entry is what the browser loads.

A rejection is an `ImportError`, a `SyncError`, so its message may be printed. Its message is composed from row numbers, field names and keys, and never repeats a header name or a cell.

### Decoding

`decode(bytes, encoding)` returns the text or rejects the file.

- **Declared `utf-8`:** decoded strictly. Bytes that are not valid UTF-8 reject the file. A UTF-8 byte order mark at the start is dropped: it is not part of the first header name.
- **Declared `windows-1252` or `iso-8859-15`:** rejected if the bytes start with a UTF-8 byte order mark, or are valid UTF-8 holding at least one multi-byte character. Otherwise decoded with that encoding.
- **Either:** a UTF-16 byte order mark rejects the file. Decoded text that holds a control character other than tab, carriage return and line feed rejects the file. That includes U+0080 to U+009F, which is what a `windows-1252` file read as `iso-8859-15` produces for the characters the two do not share.

Decoding uses `TextDecoder`, which Node ships with all three encodings.

### Reading the table

`readDelimited(text, delimiter)` returns the header and the rows.

- **Quoting follows RFC 4180.** A cell that starts with a double quote runs to the closing one, and may hold the delimiter, a line break and a doubled quote, which stands for one. A cell is stored without its surrounding quotes.
- **Line endings:** CRLF and LF both end a row. A line ending at the end of the file ends the last row and does not start an empty one.
- **The first row is the header.**
- **Rejected, each with a message that names the row by number:** a quote that is never closed; text between a closing quote and the next delimiter or line ending; a double quote inside a cell that did not start with one; a row whose number of cells differs from the header's; a header name that is empty or appears twice; a file with a header and no rows; an empty file.
- **Nothing is trimmed, skipped or guessed.** An empty line in the middle of the file is a row with one cell, and is rejected as such unless the table has one column.

Rows are numbered as a person counts them in the file: the header is row 1. A row that spans lines is numbered by where it starts in the table, not by line.

### Rows to batches

`readRows(table, formatKey, format, accounts)` returns one batch per account key, or rejects the file.

- **Every column the format names must be in the header, exactly.** A missing one rejects the file, named by the format's field (`amount`, `description, column 2`), not by the column's own name.
- **`raw`** is the row as an object from header name to cell text, every column kept, in the header's order.
- **The account** is the cell of the format's `account` column. It matches an account whose `iban` equals it once spaces are removed and case is ignored, as `auth` matches, or whose `import_id` equals it exactly. No match rejects the file. The configuration already refuses two accounts that share either.
- **The identifier** is the cell of the `id` column, as it is. An empty one rejects the file, and so does one that appears twice for the same account, whether or not the two rows are identical.
- **The date** is the cell of the `date` column, read with its notation. It becomes the record's `date`.
- **The amount and the currency** must be readable as the view reads them: three capital letters, and a signed decimal with the format's decimal mark. They are checked and not stored apart from `raw`.
- **Beyond those five, a row is not judged at import.** A value date or an original amount that cannot be read is found by the view, which names the record.

Every problem that can be found without stopping is collected, up to a limit of 20, and reported together, so one run of a check shows what is wrong with a file rather than its first row.

### The command

`import <format> <file>` checks. `import <format> <file> --write` checks and then writes.

1. Startup as every command: the environment, the two directories, the configuration.
2. The format key must be configured. If not, the command fails and lists the configured keys.
3. Read the file's bytes. A path that names no file fails with a message that does not repeat the path.
4. Decode, read the table, read the rows. Any rejection ends the command with exit 1, having written nothing.
5. For each account in the file, read its stored import records and `merge` the batch into them, with the clock's time. Before that, a stored record with one of the batch's identifiers and a different `format` rejects the file: `merge` would keep the old format key over a `raw` it does not describe.
6. Print the summary.
7. With `--write`: write each account through the store, in the order of the account keys, and print one line per account written. Without it: print that nothing was written and how to write.

**The lock and the writability check apply only with `--write`.** A check never waits for the nightly run. With `--write`, the command takes the lock before step 5, so that what it merges into is what it writes over.

**A record left in two year files by an interrupted write** is repaired first under `--write`, as the sync does for an API source. A check that meets one stops with the store's message, since a check writes nothing.

**All accounts are merged before any is written.** A file is accepted or rejected as a whole. Writing is still one account at a time, so a process that dies between two accounts leaves the first written. Running the command again finishes it, because importing the same file twice changes nothing.

**Exit codes:** 0 for a check that accepts the file and for a write that completes; 1 for anything else.

### What it prints

Through the log, as `key=value` lines of keys, dates and counts:

```text
import-account account=bnka-current rows=412 new=380 changed=0 unchanged=32 from=2021-01-04 to=2024-12-31
import-account account=bnka-joint rows=95 new=95 changed=0 unchanged=0 from=2021-02-01 to=2024-12-30
import-characters distinct=2
  U+00E9 é 14
  U+20AC € 3
import-checked format=account-export accounts=2 rows=507 written=no
Nothing was written. Run the same command with --write to import.
```

- **The character list is the one thing not made of keys, dates and counts.** It exists so that a wrong encoding can be seen ([sync.md](../sync.md)), and holds single characters with their code points. `import` is run by hand, at a terminal.
- **`changed` is a count, and a warning.** A row that differs from what is stored under its identifier becomes a revision. On a first import it should be 0; anything else on a file from the same bank is worth a look before `--write`.
- With `--write` the last two lines become one `import-written` line per account and `written=yes`.

## Configuration: two debts

The archive-format slice left both to this one ([sync.md](../sync.md)).

- **Unknown keys are rejected**, at every level of the configuration file: the top, a bank and its `aspsp`, an account, an import format and each of its column objects. A mistyped field would otherwise read as an optional one left out, and yield nulls without a word. The message names the place and the unknown key only when the key matches the key pattern; otherwise it says that the place holds a key the configuration does not know.
- **An import format's `id` column may not be named by any other field of that format.** Identifiers appear in messages, so the identifier may not be the account, the amount, a counterparty, a description or anything else the format reads.

`fixtures/config.json` must still pass, and so must the sandbox configuration in [sandbox.md](../sandbox.md).

## The view: blank cells

For an import record, the text fields of the view (`counterparty_name`, `counterparty_account`, `code`, and each description line) are trimmed of surrounding whitespace, and a cell that is then empty is absent: null, or skipped in the description. `raw` is untouched, so this rewrites nothing.

The fields read by notation (dates, amounts, currencies) are not trimmed. A padded one cannot be read, and is an error as before.

## Tests

All test data is made up, with the two formats of `fixtures/world.ts` or smaller ones written in the test. No test holds a header or a value from a real export.

**Tier 1**

- `decode`: each encoding decodes known bytes to the right text. Rejected: bytes that are not UTF-8 declared `utf-8`; multi-byte UTF-8 declared single-byte; a UTF-8 byte order mark declared single-byte; a UTF-16 byte order mark; a control character; a `windows-1252` euro sign read as `iso-8859-15`. Accepted: a byte order mark on a `utf-8` file, dropped; a plain ASCII file under each encoding.
- `readDelimited`: quoted cells holding the delimiter, a line break and a doubled quote; CRLF, LF and a missing final line ending; and each rejection in the list above.
- `readRows`: `raw` keeps every column and no value is altered; an account by IBAN with spaces and lower case, and by `import_id`; and each rejection: a column of the format missing from the header, an unknown account, an empty identifier, a repeated one, a date, an amount and a currency that cannot be read. Two accounts in one file give two batches, and the same identifier in two accounts is accepted.
- `characters`: counts, order by code point, and nothing for an ASCII text.
- Configuration: an unknown key at each level, and an `id` column shared with each kind of field.
- The view: a padded text cell is trimmed, a blank one is null, a blank description line is skipped, and a padded amount is still an error.

**Tier 2**, the real command through `main`, against a temporary directory:

- a check writes nothing, not even a directory, and takes no lock;
- `--write` writes `<account>/import/<year>.json`, and the view of what was written matches the file's rows;
- the same file twice leaves every year file byte-for-byte identical;
- an overlapping later export adds only what is new;
- a changed row becomes a revision, and is counted as changed;
- a file for two accounts lands per account;
- a file with one bad row among good ones writes nothing;
- a stored record under another format rejects the file;
- a held lock stops `--write` and does not stop a check;
- an unknown format key, and a path that names no file.

**Property**, in `sync/src/import/convergence.test.ts`: a generated export for two accounts is cut into random overlapping slices, each rendered as a file with random quoting and line endings. Imported in any order, with any slice repeated, the view equals that of one import of the whole, apart from `first_seen`. The expected set comes from the generated rows, not from the reader. Before it is trusted it is seen to fail under named breaks: dropping the last row of a file, splitting on a delimiter inside quotes, and taking the first of a repeated identifier.

**The leak test** (`sync/src/leak.test.ts`) gains `import`: a check, a write, and each kind of rejection, over a file with recognisable identifiers, amounts, IBANs, names, descriptions and header names. None may be printed. The character list is asserted apart: it holds only single characters.

## Departures and additions

Each is written into the document named before the slice is done.

- **A byte order mark on a `utf-8` file is dropped.** [sync.md](../sync.md) names the mark only as a reason to reject a single-byte file.
- **The reader is strict about quoting and row length**, and rejects a file with no rows. [sync.md](../sync.md) says nothing about the dialect.
- **How a row's account is matched.** [sync.md](../sync.md).
- **A stored record under another format rejects the file.** [archive-format.md](../archive-format.md).
- **`import --write` takes the lock; a check does not.** [sync.md](../sync.md) says only `auth` and `sync` take it.
- **The amount and the currency are checked at import**, although only the date is stored. [sync.md](../sync.md) already asks for an amount that parses; the currency is new.
- **Text cells are trimmed in the view.** [archive-format.md](../archive-format.md).
- **Unknown configuration keys, and the `id` column rule.** [sync.md](../sync.md), where they move from "owed" to the configuration section.
- **What the real files showed**, as far as it may be said. [sync.md](../sync.md), beside what the sandbox showed.

## Not in this slice

- **A quote character other than the double quote.** If a real file is rejected for a text cell that holds the delimiter inside single quotes, the schema gains a setting then.
- **An identifier made of more than one column.**
- **A direction column or separate debit and credit columns.** [archive-format.md](../archive-format.md) already says other notations are added when a bank needs them.
- **A count of the imported rows that the API start will hide from the view.**
- **Real import formats.** They name real banks through their headers and are production configuration, written by the owner on the host.
- **Feeding the fixture generator through the reader.** The generator keeps building import rows as objects.

## What moved while it was built

The reader:

- **`readRows` takes no format key.** It takes the table, the format and the accounts; the command builds the merge target.
- **`sync/src/import/error.ts` and `sync/src/iban.ts` are modules the table did not list.** The first holds `ImportError` and the function that joins problems and stops at twenty. The second holds the IBAN comparison that `auth` already had, now shared with the import.
- **`namedColumns` lives in `shared`**, beside the format's type. Both the configuration's `id` rule and the reader's check of the header need the list of columns a format names, each with the field that names it.
- **A header problem and a row-length problem are reported together; a quoting problem stops at once.** After an unclosed or misplaced quote nothing further in the file can be read with any meaning.
- **A missing column stops before the rows are read**, so its message is not followed by one line per row.
- **A currency that cannot be read hides that row's amount problem.** The number of decimals depends on the currency.

The configuration:

- **An unknown field is named only when it is made of letters and underscores.** The spec said the key pattern, which admits digits, and a key of digits could be an account number typed where a field belongs.
- **`delimiter` may not be a double quote or a line ending.** The reader could not tell such a delimiter from quoting or from the end of a row.

The command:

- **The lock is held for the whole of an `import --write`**, from before the file is read, not from the merge onward. It is simpler, and a check still takes none.
- **A format key that is not configured is not repeated**, since it is typed by a person. The configured keys are listed instead.
- **A path that cannot be read gives the error's code** (`ENOENT`, `EISDIR`, `ENOTDIR`, `EACCES`) and never the path.
- **`--write` is accepted only as the last argument**, and neither of the first two may start with `--`.
- **`import-written` reports the number of year files written**, which is 0 when nothing changed.

Tests:

- **The property's breaks are five, and not the three the spec named.** "Taking the first of a repeated identifier" cannot break a reader that refuses repeats. In its place: leaving a doubled quote doubled, matching an IBAN only as written, and not trimming in the view. Dropping the last row of a file with no final line ending fails three of the six seeds, because in the others another file holds that row; the other four fail all six.
- **The property generates no row that changes between exports.** A revision through the import is a named scenario.
- **The leak test was seen to fail** when the message for an unknown account was made to repeat the account cell.
- **Inputs the spec implied and did not name are tested:** blank lines after the last row, a column named `__proto__`, fifty thousand rows, an IBAN configured with spaces, and `--write` in the wrong position.

The run by hand:

- **It was done outside `tmp/` and without `.env.sandbox`.** The repository's settings deny the agent both, on purpose. The real `sync/src/cli.ts` was run over a made-up file in a scratch directory, with a key generated for the run and written nowhere: a check, a write, the same write again, a file lacking columns, an unknown format key and a missing argument. Each printed what [sync.md](../sync.md) says. The walkthrough in [sandbox.md](../sandbox.md), step 7, is the same run with the sandbox's own settings, and is the owner's to do.

**Left open, for the owner:**

- **Real import formats are not written yet.** They belong to the production configuration. The two profiled files fit the schema; whether a long export from either bank holds something a one-row sample did not show is found by a check on the host, which writes nothing.
- **A text cell wrapped in single quotes that holds the delimiter rejects its file.** If a check on a real export fails with a row of too many cells, the schema needs a quote-character setting.
- **An import does not say how many of its rows the API start will hide from the view.** They are stored either way.
