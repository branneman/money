# Spec: the sync

Slice 2 of the build order in [architecture.md](../architecture.md). Written 2026-10-11. Once the slice has shipped this file is history and is not kept up to date.

## Goal

Fetch booked transactions from every configured bank into the archive, unattended, so that nothing a bank returned is ever lost and a missed or interrupted night repairs itself.

After this slice the commands `auth <bank>`, `sync` and `status` exist, are tested end to end against a fake bank, and have been run once by hand against the Enable Banking sandbox. Nothing in this slice runs in production: the first real `auth` is the user's, later, and is not a test run.

[sync.md](../sync.md) is the design this spec builds. Where the two differ, the difference is listed under "Departures from sync.md" and is written into that document before the slice is done.

## What gets built

### The `sync` workspace

`sync/` becomes a workspace, `@money/sync`, depending only on `@money/shared`. The root `workspaces`, the `test` script and `tsconfig.json` list it; until they do, its tests do not run.

| Module                           | Does                                                                                           | Pure |
| -------------------------------- | ---------------------------------------------------------------------------------------------- | ---- |
| `src/cli.ts`                     | Reads argv and the environment; supplies the real `fetch`, clock and terminal; handles errors. | no   |
| `src/env.ts`                     | The environment to settings, or every problem found.                                           | yes  |
| `src/jwt.ts`                     | The RS256 token from a key, an application id and a time.                                      | yes  |
| `src/enablebanking/client.ts`    | The four requests, through an injected `fetch`. Maps error responses to typed errors.          | no   |
| `src/enablebanking/responses.ts` | Validates each response shape, and each transaction.                                           | yes  |
| `src/window.ts`                  | The fetch window for one account.                                                              | yes  |
| `src/missing.ts`                 | Stored records that a window should have returned and did not.                                 | yes  |
| `src/inbox.ts`                   | Pages and markers under `DATA_DIR/.inbox`.                                                     | no   |
| `src/state.ts`                   | One file per bank under `STATE_DIR`, validated on reading, written atomically.                 | no   |
| `src/lock.ts`                    | One run at a time.                                                                             | no   |
| `src/log.ts`                     | `key=value` lines, to an injected writer.                                                      | no   |
| `src/commands/`                  | `auth.ts`, `sync.ts`, `status.ts`, and the per-account fetch they share.                       | no   |
| `testing/fake-bank.ts`           | The in-memory bank.                                                                            | n/a  |

Every module that does I/O takes what it touches as an argument: `fetch`, the clock, the directories, the line reader, the log writer. Nothing reads `process.env`, the time or the network except `cli.ts`.

### Settings

Every command validates the whole environment and the configuration file at startup, reports every problem at once, and stops if there is one.

| Variable            | Meaning                                                      |
| ------------------- | ------------------------------------------------------------ |
| `EB_APP_ID`         | The Enable Banking application id.                           |
| `EB_PRIVATE_KEY`    | The application's private key: the PEM file, base64-encoded. |
| `EB_REDIRECT_URL`   | The registered redirect URL. Must be HTTPS.                  |
| `CONFIG_PATH`       | The configuration file.                                      |
| `DATA_DIR`          | The archive. Must exist; it is never created.                |
| `STATE_DIR`         | Sessions and sync state. Must exist; it is never created.    |
| `LOOKBACK_DAYS`     | A whole number, 0 or more. Default 30.                       |
| `CONSENT_WARN_DAYS` | A whole number, 0 or more. Default 14.                       |

- **The key arrives in a variable and no other way.** A 4096-bit key is about 4,400 characters once encoded, far below what an environment can hold. There is no `EB_PRIVATE_KEY_PATH`. This settles the open decision in [infra.md](../infra.md).
- **The base URL is a constant**, `https://api.enablebanking.com`. Sandbox and production differ by application, not by address.
- **Messages name variables, never their values.**
- `.env.example` is added, documenting each variable with no value that could be real.

### The Enable Banking client

Four requests, each with a fresh `Authorization: Bearer` token minted once per run:

| Request                            | Used by        | For                                                                                |
| ---------------------------------- | -------------- | ---------------------------------------------------------------------------------- |
| `GET /aspsps?country=<country>`    | `auth`         | The bank's `maximum_consent_validity`, in seconds, and its `required_psu_headers`. |
| `POST /auth`                       | `auth`         | The URL the user approves at.                                                      |
| `POST /sessions`                   | `auth`         | The session, its accounts and its expiry.                                          |
| `GET /accounts/<uid>/transactions` | `auth`, `sync` | One page of transactions.                                                          |

- **Transactions are asked for with `transaction_status=BOOK`.** A transaction that arrives with any other status is skipped and counted, in case a bank ignores the filter.
- **A window fetch** sends `date_from` and `date_to`. **A backfill** sends `strategy=longest` and no dates.
- **No PSU headers are sent**, by any command. If a bank requires them, its error stops that bank loudly.
- **Each request has a time limit**, and there are **no retries** anywhere. Banks allow few unattended fetches a day.
- **An error response** becomes a typed error holding the HTTP status and the response's `error` code, when that code is made of capitals and underscores. The response's `message` and `detail` are never kept or logged. `EXPIRED_SESSION`, `REVOKED_SESSION`, `CLOSED_SESSION` and `SESSION_DOES_NOT_EXIST` mean the consent is gone, and the message says to run `auth <bank>`.
- **`auth` asks for a personal consent**, for transactions only, valid for the bank's `maximum_consent_validity` from now.

**Validation on arrival.** Each response is checked for the fields the code reads, by type. A page must be an object whose `transactions` is a list and whose `continuation_key`, when present, is a non-empty text. Each transaction must be an object with a text `status`. A `BOOK` transaction must have a non-empty text `entry_reference` and a `booking_date` that is a real calendar date; a missing one is an error, never a reason to match on content.

**Numbers.** `raw` is compared, night after night, with a copy that has been through JSON. A page is therefore parsed with a reviver that sees each number's source text, and a number whose text differs from how JSON would write it back (`1.10`, an integer too large to hold) is an error. Amounts are text in this API, so this should never fire; if it does, the archive would otherwise show a revision every night.

### One account's fetch

The same two phases for a backfill and a nightly fetch. The inbox is the only way data moves from the first to the second: the merge reads pages from disk and never from memory, so a fresh fetch and one left by a crash take the same path.

```text
$DATA_DIR/.inbox/<account key>/<run>/
  1.json  2.json  ...     the pages, exactly as received
  complete.json           the marker
```

`<run>` is the run's start time, `YYYYMMDDTHHMMSSZ`.

1. **Receive.** A response with status 200 whose body parses as JSON is written, byte for byte as received, to a temporary file and renamed into place. Only then is it validated far enough to find the `continuation_key`, and the next page requested. When no key remains the marker is written, holding the run's start time, its strategy, its window and its page count.
2. **Merge.** Every run in the account's inbox is merged, oldest first. Each page is validated in full, non-`BOOK` transactions are dropped and counted, and the rest go to `merge` with a timestamp in whole seconds.
3. **Finish.** The year files are written through the store. Then, for a completed run, the state is written. Then the run's directory is removed.

Before step 1, any run already in the inbox is merged, by steps 2 and 3:

- **A completed run** is merged exactly as if it had just been fetched, and its success recorded with the start time its marker holds. The bank is not asked again for it.
- **An incomplete run** is merged too. Each page present is whole, because of the rename, and is exactly what the bank sent, and a partial batch cannot do harm because `merge` never deletes. No success is recorded for it and no missing-record check is made, since the window was not covered. A half-finished backfill's pages therefore reach the archive rather than waiting in the inbox.
- **A run that fails validation stays where it is and stops its account**, every night, until the code is taught to read it or the user removes it. Fetching past it could put revisions in the wrong order, and removing it would discard something a bank sent.

### The fetch window

| The account has     | Fetch                                                                                          |
| ------------------- | ---------------------------------------------------------------------------------------------- |
| a recorded success  | `date_from` = the UTC date of that success minus `LOOKBACK_DAYS`; `date_to` = today's UTC date |
| no recorded success | `strategy=longest`, no dates                                                                   |

- **A success is recorded as the run's start time**, read from the clock before the first request, so a transaction booked while the run was in progress is inside the next window.
- **Missed nights catch up on their own**, since the window is anchored on the last success.
- **There is no clamp.** If a bank refuses a window that reaches further back than it serves unattended, that account fails with a message that says to run `auth`, which fetches with the user present.
- The rule applies to `auth` and `sync` alike. `auth` on a new account backfills; `auth` on a renewal fetches from the last success; a `sync` that finds an account without a success, because its backfill died, asks for the longest period again.

### Missing records

After a completed window fetch is merged: every stored API record of the account whose `date` lies inside the window and whose `id` was not in the fetch is **missing**. The record is kept, as always.

- A missing record means a bank withdrew a booking or changed an identifier. Either needs a person.
- The account's state holds the ids currently missing. An id that is missing now and was not in that set is **newly missing**, and makes the run exit non-zero, naming the account key and the count. The set is then replaced by the ids missing now, so one withdrawn transaction alerts once and not every night it stays inside the lookback, and the set empties itself as records leave the window.
- The check is strict: it covers the whole requested window. It is not made for a backfill, whose reach is not known, nor for an incomplete run.

### State

One file per bank, `$STATE_DIR/<bank key>.json`, written to a temporary file and renamed, and validated when read.

```json
{
  "session_id": "00000000-0000-4000-8000-000000000000",
  "valid_until": "2027-04-09T10:00:00Z",
  "accounts": {
    "bnka-current": {
      "uid": "00000000-0000-4000-8000-000000000001",
      "last_success": "2026-10-11T03:00:00Z",
      "missing": []
    }
  }
}
```

- `auth` writes `session_id`, `valid_until` and each `uid`. A renewal replaces those and keeps `last_success` and `missing`.
- `last_success` is absent until the account's first completed fetch has been written.
- State is written only after the data it describes. A crash between the two leaves a completed run in the inbox, and the next run records the success without asking the bank.
- Losing the state loses nothing permanent. After a new `auth`, every account has no recorded success and is fetched as far back as the bank gives, into the existing archive.

### The lock

`auth` and `sync` take `$STATE_DIR/lock`, a file created exclusively and holding the process id, and remove it when they end. If it exists and its process is alive, the command stops and says so. If its process is gone, the lock is taken over. `status` reads only and takes no lock.

The store assumes one writer per account and source. Without the lock, a manual run overlapping the nightly one could overwrite what the other had just written.

### `sync`

1. Take the lock. Check `DATA_DIR`. Recover any account left with a record in two year files (see below).
2. For each bank with at least one open account that has an `iban`:
   - No state file: the bank fails, with the message to run `auth <bank>`.
   - `valid_until` has passed: the bank fails the same way, and no request is made.
   - Otherwise, for each such account in turn: merge what the inbox holds, then fetch and merge.
3. **Accounts fail separately.** One account's failure does not stop the bank's other accounts, unless the error says the consent is gone. One bank's failure never stops another bank.
4. Log a line per account: its key, the window, and the counts of pages, added, revised, unchanged, skipped and missing.
5. Log a warning for each consent that expires within `CONSENT_WARN_DAYS`. This does not change the exit code; `status` is what alerts.
6. Exit non-zero if any bank or account failed, or any record is newly missing, after everything that could be done has been done.

### `auth <bank>`

1. Take the lock. Read the bank's entry from `GET /aspsps` by its exact configured name. Print which PSU headers it lists as required, by name.
2. `POST /auth` with a random `state`. Print the URL.
3. Read the pasted redirect URL. It must begin with `EB_REDIRECT_URL`, carry the same `state`, and carry a `code`. An `error` parameter stops the command.
4. `POST /sessions`. Match the session's accounts to the bank's configured ones by IBAN. A configured, open account with an `iban` that the session does not cover, or covers without a `uid`, is an error that names its key. Accounts in the session that are not configured are counted and ignored.
5. Write the state.
6. Fetch every matched account, by the same code as `sync`. If a fetch fails, the session is already stored and the command exits non-zero, saying that `sync` will continue the fetch.

### `status`

Makes no request. Prints, per bank, the date the consent expires and the days left, and per account the date of its last success. Exits non-zero when a bank that has an account to fetch has no state, or its consent has expired or expires within `CONSENT_WARN_DAYS`.

### Recovery for a record in two year files

An interrupted write can leave one record in two year files: its earlier version in the year it left, and its revised version in the year it moved to. Reading reports that and stops, which would stop the account for good.

`@money/shared` gains a pure function that, given the two copies, returns the one to keep **only when** it is the other with exactly one more revision whose `raw` is the other's current `raw`. `@money/shared/node` gains a recovery that reads one account and source without the duplicate check, resolves each doubled record with that function, and writes the result through the ordinary write plan. Any pair of copies that is not that shape stays an error. `sync` and `auth` run the recovery before reading; it changes nothing when nothing is doubled.

### Logs and errors

- **Lines are `key=value`**, holding keys, dates, counts and codes. Never an amount, an IBAN, a name, a description or a session id. The lines the sync composes hold no transaction identifier either; an error raised by the archive code may name a record by its identity (`account/source/id`), as [archive-format.md](../archive-format.md) already allows.
- **The top-level handler prints a message only for the project's own error classes**, whose messages the code composes from keys and positions. Any other error prints its class name and its `code` and nothing else: a filesystem error carries host paths, and a JSON syntax error quotes the text it failed on.
- Every failure exits non-zero.

## Tests

### Tier 1

- `env`: one test per rule; every problem is reported together; no message holds a value.
- `jwt`: header, claims and lifetime, verified against a throwaway key generated in the test.
- `responses`: every unexpected shape named above fails with a message that names the field and the position; a number that would not survive JSON fails.
- `window`: an account with no success; a normal night; missed nights; the year boundary; and UTC dates on both sides of midnight in the pinned zone.
- `missing`: inside and outside the window, on its first and last day; newly missing against already reported; the set emptying.
- `state`: a round trip; each malformed file is refused; a renewal keeps `last_success` and `missing`.
- `client`: each error code maps to its typed error; `message` and `detail` are not kept.
- The pure recovery function in `shared`: the interrupted-write pair resolves; every other pair is refused.
- **The log test**: a sync over transactions with recognisable amounts, IBANs, names and descriptions, including failures of every kind, and nothing logged holds any of them.

### Tier 2

The real commands, against the fake bank and a temporary directory.

**The property.** Generate a bank history whose transactions appear, change and are occasionally withdrawn over time, and a schedule of nights: skipped nights, repeated runs, both sides of a year boundary, and crashes injected at the nth request and between the steps of finishing. Run it, ending with a backfill. The normalised view must equal the view from a single fetch of the final state, plus the withdrawn records, and every version the bank ever returned must be in the archive as a current `raw` or in `revisions`. A failure prints its seed. Because the final backfill would repair a transaction that a nightly run had wrongly skipped, the property also checks the archive just before it: every transaction that never changed, and that the bank had by the last fetch recorded as a success, must already be there.

Before it is trusted, the property is seen to fail under named deliberate breaks: dropping an incomplete run, merging only the run just received (which is what merging from memory amounts to), and ignoring the lookback. Recording state before data is not among them: with the inbox, that order alone loses nothing, because the run is still there to be merged again.

**Named scenarios**, each from [testing.md](../testing.md): a second run that changes no byte; pagination followed to the end; a page that fails halfway; a transaction changed between runs; a transaction withdrawn, kept and alerted once; a crash between the temporary write and the rename; a crash after receiving and before merging, finished without a request; a backfill that dies halfway and keeps its pages; one bank's consent expired while the others sync; state written after data; an expired consent that makes no request and says to run `auth`; and no PSU header on any request the fake received. Added by this slice: accounts failing separately; a run that fails validation blocking its account and nothing else; the lock held by a live and by a dead process; a record in two year files recovered; `auth` end to end, including a wrong `state`, an account the consent does not cover, and a renewal.

### The fake bank

A real implementation of the four endpoints, held in memory and handed over as `fetch`.

- It **verifies the token's signature**, issuer, audience and lifetime, against the public half of the test's key.
- It holds a history in which each transaction has versions over time, and answers from that state and the shared clock.
- It pages, with continuation keys it checks, honours `date_from`, `date_to`, `strategy` and `transaction_status`, and reaches further back for a session that was just authorised than for an older one.
- It runs the authorisation: a URL, an approval that yields the redirect, a code that works once, sessions that expire.
- It records every request, and can be told to fail the nth one, with a given error code or a broken connection.

### The sandbox pass

Once, by hand, before the slice is done. The user registers a sandbox application and writes `.env.sandbox`, with `DATA_DIR` and `STATE_DIR` under `tmp/sandbox/` and a configuration file beside them; all of it is gitignored. Then `auth`, `sync` twice, and `status` are run. The second `sync` must change no byte.

Wherever the real API differs from the fake, the fake and the validation are corrected, by shape and never by copying a value. This is also the first evidence for the open questions in [sync.md](../sync.md), though the sandbox cannot settle what a real bank does.

## Departures from sync.md

Each is written into [sync.md](../sync.md) before the slice is done.

- **An incomplete run is merged**, not left alone.
- **The backfill is for an account with no recorded success**, not one with no API records.
- **A newly missing record makes the run exit non-zero**, once per record, instead of only logging a warning.
- **Accounts fail separately**, as banks already did.
- **The private key is `EB_PRIVATE_KEY`**, base64, and nothing else.
- **A lock** allows one writing command at a time.
- **The two-year clamp** named in [testing.md](../testing.md) is not built, and is removed from that list.

## Not in this slice

- `import`, and import formats.
- The image, its `.dockerignore`, and the job that builds it.
- Anything about monitoring. The host's wrapper reports each job's exit code and output; the sync's part is to exit non-zero when a person is needed and to print nothing that may not leave the host.
- PSU headers, closing a replaced session, and business consents.
- A contract test against the sandbox that runs by itself. That is Tier 4.

## What moved while it was built

The command line and startup:

- **The command is `main.ts`, and `cli.ts` is only the edge.** `main.ts` reads the arguments, loads the settings, takes the lock and runs the command, with everything it touches passed in, so the tests run that very function. `cli.ts` supplies the real environment, clock, network, terminal and process table, and prints what may be printed about a failure. `startup.ts`, `atomic.ts`, `consent.ts`, `redirect.ts`, `time.ts`, `errors.ts` and `context.ts` are small modules the table did not list.
- **Startup reports in two stages**, not every problem at once. First every problem in the environment; then, once the environment is sound, the two directories and the configuration file. The later checks need values the environment supplies.
- **A `CONFIG_PATH` that names no file is one problem**, whether the file is absent, is a directory, or sits under a parent that is not a directory.
- **Startup comes before the lock, and `DATA_DIR` is proven writable under it.** Startup checks only that the directory exists, and everything before the first page only reads. So `auth` and `sync` create `DATA_DIR/.inbox` if it is absent, write a dot-prefixed file in it and remove it, before any request. `status` does not, since it never writes. Recorded in [sync.md](../sync.md).

The client:

- **A token is minted for each request**, not once per run. A token lasts an hour, and an `auth` can wait longer than that for the user, or fetch for longer.
- **The exact-number rule is for pages only.** The list of banks, an authorisation and a session are parsed as plain JSON, because only pages are stored, and a number in a field nobody reads must not refuse a session after its one-time code is spent.
- **`valid_until` must be an RFC 3339 time**, with `Z` or a numeric offset and a real calendar date. Anything else stops `auth`. It is stored as a UTC timestamp in whole seconds.
- **In the list of banks only the entry asked for is checked.** Any other entry is passed over, one that is not an object included. The entry's `required_psu_headers` must be a list of header names, since they are printed.
- **A repeated `continuation_key` stops the account** with an error. Following it would never end.
- **A request that gets no answer is reported by the error's name** when that is a plain word, so a timeout says `TimeoutError`, and otherwise by its class.

The fetch and the inbox:

- **"As received" means the text the response decodes to as UTF-8**, not byte for byte. A byte order mark is dropped and a byte sequence that is not valid UTF-8 becomes U+FFFD. The inbox is a buffer against a run dying, not a forensic copy.
- **A run is merged one page at a time** and written once. A transaction that changed at the bank between two pages is then a revision instead of a contradiction, and one write can add several revisions to a record.
- **A merged run is removed in two steps.** Its directory is renamed to `.removed-<run>` and then deleted, and a `.removed-*` left by an earlier removal is deleted first. Names that start with a dot are never listed as runs or pages.
- **A page the merge refuses is named by account, run and page, with no identifier.** The spec lets an archive error name a record by its identity. This one would name a transaction by an identifier that has come from a response and is stored nowhere yet, on a line printed every night for as long as the run stays.
- **A blocked run's failure is followed by a line that says where it is**: the run's name, that it stays in `.inbox/<account>/<run>` and stops the account until it can be read, and that nothing has been removed.
- **Recovery and the inbox merge happen per account, as it is fetched**, not for every account at the start of the run. An account that is not fetched keeps what its inbox holds, and nothing reports it. The cases are listed in [sync.md](../sync.md).
- **The alert for a newly missing record is printed before the state is written.** A run that dies between the two says it again on the next run. The other order could drop the only alert.

`auth`:

- **What can be found out before the bank visit is.** Before `GET /aspsps`, `auth` reads the bank's stored state, and for each account repairs a doubled record, reads its API records and lists its inbox runs. State, a year file or an inbox run the code cannot use stops the command there. Nothing is merged at that point.
- **The longest period is decided from the state as `auth` finds it.** An account with no recorded success then is asked for the longest period, even when a completed run left in the inbox has just recorded one. So after lost state `auth` always reaches as far back as the bank gives, which the spec's two statements on this did not settle between them.
- **After a fetch that is not whole, `auth` says to run `auth` again now**, not that `sync` will continue. The nightly `sync` would ask for the longest period unattended, get what the bank then serves, and record that as the account's first success.
- **An unexpected error after the consent is stored prints the same line first**, naming every account of the bank, and then stops the command as it would anywhere. The user has been to the bank and must learn that the consent is kept.
- **The pasted address must have the origin and path of `EB_REDIRECT_URL`**, not merely begin with it. An `error` parameter is repeated only when it is a plain lower-case code.
- **IBANs are compared without spaces and case.** A configured account whose IBAN matches more than one account in the consent is an error that stores nothing; `auth` never picks one.
- **Input that ends at the prompt fails the command**, with "no address was given", exit 1 and the lock released.
- **A renewing `auth` exits 1 for a newly missing record**, as `sync` does.

`sync` and state:

- **"One bank's failure never stops another bank" holds for failures the code expects**: an API error, an expired or absent consent, a response that fails validation, state the sync did not write. An error it did not anticipate stops the whole run, later banks included, and prints only its class and code. Such an error means the program or the host is not as assumed.
- **An account the stored consent does not cover fails alone**, with the message to run `auth`, and the bank's other accounts are fetched.
- **A state file that is not what the sync wrote fails its bank**, with a message that says to remove it and run `auth`.

The lock:

- **It is created by linking, not by an exclusive create.** Its content is written to a temporary file that is linked to the lock's name, so the lock is never seen empty. `STATE_DIR` must therefore be on a filesystem with hard links. Recorded in [infra.md](../infra.md).
- **Its content must be a plain positive integer.** Anything else is a stale lock, as is one that names the command's own process id, because ids repeat inside a container.
- **A stale lock is taken over by renaming it aside** and checking that what was moved is what was judged stale. Releasing removes the lock only if it still holds this process's id.

Recovery:

- **The later copy may be one or more revisions ahead**, not exactly one, the first added revision holding the earlier copy's `raw`. A run is merged page by page and written once, so an interrupted write can leave a pair two revisions apart. Recorded in [archive-format.md](../archive-format.md).

Tests:

- **The log test drives the real commands**, in `sync/src/leak.test.ts`, and is not a unit test. It plants transaction identifiers, the key, the session and the account `uid`s besides amounts, IBANs, names and descriptions, and each test checks that the path it scans was reached.
- **A run that dies is reproduced with a checkpoint**: a function the commands call at four named points, which production leaves empty and a test makes throw.
- **The fake bank is stricter than the spec asked.** It records each continuation key it issues and accepts one only for the same account and the same query, works out a paged answer once, at its first page, and refuses unknown or malformed query parameters. A lenient fake would let the commands' tests pass for the wrong reason.
- **The property runs 9 seeds of 20 nights**, with one bank and one account, so that it fits in the pre-commit hook. Isolation between accounts and banks is left to the named scenarios.
- **Its schedule is biased.** A night that leaves something in the inbox is usually followed by a change at the bank to a transaction served during that interrupted run, because those are the only schedules in which losing an inbox run loses a version.
- **Its oracle is the bank's own log of what it served**, checked in both directions, and it compares with Node's own deep equality, so it shares no helper with the merge it judges. Coverage guards fail the test if the schedules stop reaching what it exists for.
- **It was seen to fail under four breaks, not three.** The fourth is merging only the first page of an incomplete run. Recorded in [testing.md](../testing.md).

**Left open, for the owner:**

- **The lock only excludes runs that share a process-id namespace.** If the nightly job and a manual `auth` each run as process 1 in separate containers over one `STATE_DIR`, neither excludes the other. How the commands are run is the infra repo's decision.
- **No directory is flushed after a rename.** The guarantees are against the process dying. Under power loss the order relied on across the year files, the state and the inbox rests on the filesystem.
- **The files are written with the default mode.** Whether the state, the inbox and the year files need a narrower one is not decided.
- **Should an unattended longest-period fetch that completes count as an account's first success?** Today it does, so a first `auth` that is not whole, followed by the nightly job, gives up the older history without a word. The message and the runbook say to run `auth` again first; nothing enforces it.
- **The "consent is stored" line is the same on a renewal**, where the fetch has a dated window and `sync` is the right continuation, and after an unexpected error it names every account, fetched or not. The cost is at worst one needless bank visit.
- **One account's unreadable archive or blocked inbox run stops `auth` for its whole bank**, before the bank visit. If the consent expires before the repair, the whole bank stops, not the one account.

**What the sandbox pass changed, on 2026-10-13:**

- **`banks <country>` was added.** The spec has the bank's name read from `GET /aspsps` and gave no way to read it. The command prints the names for one country, and `auth` points to it when it finds no match.
- **An account the consent does not cover is followed by a count** of the accounts the consent holds and how many carry an IBAN, so a wrong IBAN can be told from a bank that names accounts another way.
- **`auth <bank> --show-ibans` was added**, the one place an IBAN is printed, and only when asked. A sandbox bank's test accounts are published nowhere, and the configuration needs one.
- **Nothing in the validators or the fake bank had to change.** `auth`, two runs of `sync` and `status` worked against one sandbox bank at the first complete attempt, and the second fetch of a window found every transaction unchanged. [sync.md](../sync.md), "What the sandbox showed", has what was and was not observed.
- **`sync/src/cli.ts` is still run by no test.** The sandbox pass was its first run.
