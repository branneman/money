# Spec: the image

Slice 4 of the build order in [architecture.md](../architecture.md), added on 2026-10-14 between the import and the dashboard. Written 2026-10-14. Once the slice has shipped this file is history and is not kept up to date.

## Goal

Make the sync deployable: a container image that CI publishes, holding the command line and nothing else, so that the nightly sync and the backup can run in production before the dashboard exists.

After this slice every push to `main` publishes an image, and a container started from it can run `auth`, `sync`, `status`, `banks` and `import`. Nothing in this slice touches a host. Declaring the container, its volumes, its schedule and its backup is the infra repo's work, specified there, and the first production run is the user's.

[infra.md](../infra.md) is the design this spec builds. Where it differs from that document, or settles what it left open, the point is listed under "Departures and additions" and is written into the document that owns it before the slice is done.

## Why now

Nothing in `sync` waits on `api` or `app`, and waiting costs history: a bank serves a limited period unattended, so every month without a nightly run is a month that later has to come from a hand export. The first real authorisation, a consent that expires, the nightly schedule and the restore check have also only ever met a fake bank and one sandbox run. They get weeks of real nights before the dashboard depends on them.

### The image

- **One stage, for now.** The base is the official Node 24 image in its small variant, pinned by digest. There is nothing to bundle until `app` exists; the second stage arrives with the dashboard.
- **It holds the server's source and the workspace links.** `package.json`, `package-lock.json`, `shared/` and `sync/` are copied in, and `npm ci --omit=dev --ignore-scripts` then creates `node_modules/@money/`, which holds links to the workspaces and nothing else. Node needs those links to resolve `@money/shared`.
- **What stays out.** `.dockerignore` refuses everything and then admits the four paths above, so a new top-level folder is out of the image until someone lets it in. Test files (`*.test.ts`) and the `testing/` folders are left out too. Fixtures, docs, scripts, `tmp/` and any `.env` file never reach the build.
- **A non-root user.** The image runs as the base image's `node` user.
- **Two directories to mount over: `/data` and `/state`**, created in the image and owned by that user. A new volume takes its ownership from the directory it is first mounted over, so the container can write without setup on the host. The image sets `DATA_DIR=/data` and `STATE_DIR=/state`. The directory for rules arrives with the dashboard.
- **`CONFIG_PATH` is not set.** Where the configuration file is mounted is the host's choice, and a container without it fails at startup, as every command does today.
- **The command is `money`.** `bin/money` is a two-line shell script on the path that runs `node /app/sync/src/cli.ts` with its arguments. A person typing `money auth bnka` years from now should not need to remember a path inside the image.
- **By default the container idles.** Its command is `sleep infinity` and its stop signal is `SIGKILL`. The container exists to be run in; nothing in it handles a signal, and a run that is killed is already safe ([sync.md](../sync.md)). Without the stop signal every deploy would wait ten seconds for a process that cannot answer.
- **It says which commit it is.** The build takes the commit as an argument and records it as the image's `org.opencontainers.image.revision` label, with the source repository beside it.

### Publishing

Two CI jobs, after the two that exist:

- **`image`, on every push and pull request,** builds the image and runs `scripts/check-image.sh` against it. A Dockerfile that no longer builds is found on the branch, not on `main`. It reads the repository and nothing else.
- **`publish`, on a push to `main` only, and only once the other three have passed,** builds and checks the image again and pushes it to GHCR as `:<commit-sha>` and then `:latest`, so `:latest` never names an image whose commit tag is missing. It builds again rather than taking the first job's image, because a job that runs a branch's Dockerfile should never hold a token that can write packages.
- **`publish` is the only job that may write packages**, and it uses the workflow's own token. The workflow still holds no secret. Every other job keeps `contents: read`.
- **No new action.** The jobs use `docker build`, `docker login` and `docker push` from the runner, so nothing third-party joins the workflow.

`scripts/check-image.sh <image>` asserts, by running the image:

- `money` with no argument prints the usage line and exits non-zero;
- `money status` without configuration exits non-zero and names the missing variable;
- `money import` of a made-up file, against a made-up configuration mounted into the container, checks it and prints the summary: the one run that crosses `sync`, `shared` and the store inside the image;
- `/data` and `/state` exist, are owned by the user the image runs as, and are writable by it;
- `node_modules` holds only `@money`;
- no file in the image is named `*.test.ts`, and `fixtures`, `docs`, `tmp` and `.env*` are absent.

It is a shell script because it tests the one thing in this repository that is not TypeScript, and it runs the same way on a laptop.

### A first success needs the user present

This settles the open question in [sync.md](../sync.md).

Today a completed fetch of the longest period records the account's first success, whoever started it. When a first `auth` leaves an account not fetched in full and the nightly `sync` reaches it first, the success is recorded on what the bank serves unattended, and the older history is never asked for again. Only the order of two commands prevents it.

After this slice:

- **A run's marker says whether the user was present.** `auth` starts its fetches with the user present; `sync` never does. The marker written when a run is received in full carries `attended: true` or `false`, and a marker without the field is not one the sync wrote.
- **A completed longest-period run records a success only when it was attended.** An unattended one is merged like any other, its pages are removed from the inbox, and the account's state is left as it was.
- **`sync` then fails for that account.** It prints `<account>: fetched without a first success, so the bank gave only what it serves unattended. Run: auth <bank>` and exits 1. Exit codes are the alerting interface, so the owner hears of it the next morning and every morning after, until an `auth` with the user present completes.
- **Nothing is lost in the meantime.** Each night's unattended fetch is merged, so recent transactions keep arriving. What waits is only the older history, which only the user's presence can unlock.
- **A dated window is unchanged.** Once an account has a success, every fetch is a window from it and records its success as before.

The cost: an account whose attended longest-period fetch can never complete would fail the nightly run for ever. No bank is known to behave so. If one does, the answer is a deliberate way to declare an account's history complete, designed then.

### The two things the import left

- **A carriage return that does not end a line rejects the file.** Outside a quoted cell, a carriage return not followed by a line feed is refused, with the row's number. Today it is stored as part of its cell, and a file that uses carriage returns alone is refused as "a header and no rows", which sends the reader looking for the wrong fault. Inside a quoted cell a carriage return is data, as it is now.
- **A repair under `--write` is said.** When `import --write` repairs a record that an interrupted write left in two year files, it prints the `recovered` line the sync prints, with the account and the count.

## Running it

What the image promises the host, and so what [infra.md](../infra.md) says after this slice:

- **One container, kept running, and every command run inside it.** `auth`, `sync` and `import --write` exclude each other by a lock that names a process id, which works only inside one container.
- **A lock can outlive its container.** A deploy that lands mid-run kills the run and leaves its lock. The next run takes it over when the process it names is gone, or has the run's own id. If another process in the new container happens to have that id, the run refuses and says which file to remove. It is loud, rare, and one command to fix.
- **An export file reaches the container through a read-only mount.** The host mounts a directory of its own choosing; the user copies the file there, runs `money import <format> <file>`, reads the summary, runs it again with `--write`, and deletes the file. Nothing of the export is ever written inside the container, so there is nothing to clean up in it. The exact commands name the host, and are documented in the infra repo.
- **The configuration file must be readable by the image's user.** How the host arranges that is the host's business.

## Tests

- **Tier 1:** the marker with and without `attended`; a completed unattended longest-period run leaves the state without a success; an attended one records it; the reader refuses a lone carriage return outside quotes and keeps one inside.
- **Tier 2,** the real `sync` and `auth` against the fake bank:
  - a first `auth` whose fetch of one account fails, then `sync`: what the bank serves unattended is merged, a transaction older than that is not there, no success is recorded, and `sync` exits 1 with the line above; a second `auth` then asks for the longest period, stores the older transaction, and records the success;
  - `sync` on its own for an account that never had a success does the same every night, and its archive is the same as after one such night;
  - the convergence property is unchanged and still passes. Its first authorisation always completes, so it never meets an unattended first fetch; that case has the two scenarios above;
  - `import --write` over a record left in two year files prints the `recovered` line.
- **The leak test** covers the new line.
- **The image,** in CI on every push: `scripts/check-image.sh`.

Each new test is seen to fail first.

## Not in this slice

- **Anything on a host.** The container's declaration, volumes, schedule, backup, restore check and the runbook are specified in the infra repo.
- **The web container,** its port, health and version endpoints, and the second build stage.
- **Rebuilding on a schedule.** The image is rebuilt when `main` moves. A fix in the base image arrives with the next push, or when the pinned digest is moved by hand.
- **The first production run.** The volumes, the first `auth` and the first import are the user's.

## Left open, for the owner

- **The package's visibility.** GHCR creates a package private. It has to be made public once, by hand, after the first push, or the host cannot pull it.
- **A sandbox inbox from before this slice** holds markers without `attended`, and is refused. Empty `tmp/sandbox/data/.inbox` if it holds any run.

## What moved while it was built

Everything below is written into the documents that own it. This section is only the record of where the build differed from the text above.

- **One existing `sync` test changed its expectation.** "A backfill that died during auth is continued by sync, asking for the longest period again" now expects `sync` to exit 1, where it expected 0. Its premise is exactly the case the new rule changes: `sync` still stores what it fetched, but the account fails until `auth` has been run.
- **One existing `import` test changed the line it reads.** The repair line now comes first in the output, so the test that asserted the summary at the first line no longer does. It still asserts the summary, not at a fixed line.
- **`.dockerignore` admits five paths, not four.** `bin/money` is let in beside `package.json`, `package-lock.json`, `shared/` and `sync/`, because the image copies it onto the path.
- **`bin/money` sits at the repository root,** not under `sync/`. It is the image's entry point, not part of the workspace.
- **The CI jobs' YAML was indented under `jobs` by the implementer,** because the plan's blocks had lost their leading indentation. A parse confirmed the structure the spec describes: `publish` needs the other three jobs, runs on `main` only, and is the only job with `packages: write`.
- **`docs/testing.md`'s list of the reader's refusals** also gained the lone carriage return, and its CI table the two new jobs.
- **`docs/infra.md`'s account of the `.dockerignore`** was corrected to match: it said the file kept out `test/`, a folder that does not exist.
- **The package came out public.** The first push from `publish` left an image that pulls without a login, by tag and by commit, so the step "Left open, for the owner" names was not needed. `docs/infra.md` says so now.

### Left open

Found in review and not done in this slice; each is small.

- **`publish` has no concurrency group.** Two quick pushes to `main` could leave `:latest` on the older commit.
- **`publish`'s checkout keeps the token in `.git/config`,** while the build and the check run. `persist-credentials: false` closes it.
- **`.dockerignore` does not exclude a nested `node_modules`** under `shared/` or `sync/`, and nothing checks for one.
- **The image check's ownership step was never seen to fail under a break.**
- **The fetch takes two adjacent booleans** (`backfill`, `attended`), which are easy to transpose.
- **The test named "is continued by sync" no longer says the account fails,** and does not assert the new line.
- **The pinned summary position in the two-year-files import test** is loosened to anywhere in the output.
- **`scripts/check-image.sh`:** a failing `docker run` in the later checks aborts without a `FAIL` line; it must be run from the repository root; and it uses neither `--pull=never` nor `--network none`.
